# CI/CD Pipeline & GitHub OIDC Documentation

## 1. Pipeline Overview

The deployment pipeline is built using **GitHub Actions** and implements GitOps principles for Infrastructure as Code. Every commit and pull request triggers automated validation, formatting checks, and security scans. Merges to the `main` branch trigger automated, controlled Terraform deployments.

```
                    +---------------------------+
                    | Push / PR to main branch  |
                    +---------------------------+
                                  |
                                  v
+---------------------------------------------------------------------------------+
| Job 1: Lint & Format Check                                                      |
|   • terraform fmt -check -diff -recursive                                        |
|   • terraform validate (Root, Dev, Prod modules)                                |
+---------------------------------------------------------------------------------+
                                  |
                                  v
+---------------------------------------------------------------------------------+
| Job 2: Security & Static Code Analysis                                          |
|   • Trivy IaC Security Scanner (CRITICAL, HIGH findings)                        |
|   • Misconfiguration checks against CIS AWS Benchmarks                          |
+---------------------------------------------------------------------------------+
                                  |
                                  v
+---------------------------------------------------------------------------------+
| Job 3: Terraform Plan (via GitHub OIDC)                                         |
|   • Assume IAM Role via OIDC (Zero static credentials)                         |
|   • Query S3 Remote State + DynamoDB State Locking                              |
|   • Generate speculative plan (tfplan)                                          |
|   • Post plan summary comment to Pull Request                                   |
+---------------------------------------------------------------------------------+
                                  |
                   [ Merge / Push to 'main' ONLY ]
                                  v
+---------------------------------------------------------------------------------+
| Job 4: Terraform Apply                                                          |
|   • GitHub Environment approval gate (production)                               |
|   • Execute: terraform apply tfplan                                             |
|   • Publish Live HTTPS Application URL to $GITHUB_STEP_SUMMARY                  |
+---------------------------------------------------------------------------------+
```

## 2. GitHub OIDC Authentication vs Static Access Keys

### Why OpenID Connect (OIDC)?
Traditional CI/CD pipelines store long-lived IAM access keys (`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`) in GitHub repository secrets. If compromised, an attacker retains indefinite access until keys are manually revoked.

With GitHub OIDC:
1. GitHub Actions requests a JSON Web Token (JWT) from GitHub's token service.
2. The workflow exchanges this JWT with the AWS Security Token Service (STS) using `sts:AssumeRoleWithWebIdentity`.
3. AWS STS validates the JWT signature against GitHub's public keys (`token.actions.githubusercontent.com`) and verifies the repository subject claim (`repo:OWNER/REPO:*`).
4. AWS STS returns temporary credentials that expire in 1 hour.
5. **No static secrets exist in GitHub**.

## 3. GitHub Secrets vs Variables Configuration Matrix

To maintain least privilege and avoid storing non-sensitive data in secrets, follow this exact configuration matrix:

### A. GitHub Secrets (Repository Secrets)
Stored under `Settings > Secrets and variables > Actions > Secrets`:

| Secret Name | Required? | Example Value | Description |
|---|---|---|---|
| `AWS_ROLE_ARN` | **Yes** | `arn:aws:iam::123456789012:role/savitara-dev-github-actions-role` | The ARN of the IAM role configured with GitHub OIDC trust policy. |

> [!NOTE]
> **What does NOT need to be stored as a secret:**
> - `AWS_ACCESS_KEY_ID`: **NOT NEEDED** (Eliminated by OIDC).
> - `AWS_SECRET_ACCESS_KEY`: **NOT NEEDED** (Eliminated by OIDC).
> - Database password: **NOT NEEDED** (Dynamically generated by Terraform and stored in AWS Secrets Manager).
> - AWS Region, bucket names, project names: **Store as Variables, not Secrets**.

### B. GitHub Variables (Repository Variables)
Stored under `Settings > Secrets and variables > Actions > Variables`:

| Variable Name | Required? | Example Value | Description |
|---|---|---|---|
| `AWS_REGION` | **Yes** | `us-east-1` | AWS region where resources and state are provisioned. |
| `TF_STATE_BUCKET` | Optional | `savitara-terraform-state-123456789012` | Name of the S3 bucket used for remote state backend. |
| `TF_STATE_DYNAMODB_TABLE` | Optional | `savitara-terraform-locks` | Name of the DynamoDB table used for Terraform state locking. |
| `ACM_CERTIFICATE_ARN` | Optional | `arn:aws:acm:us-east-1:...` | ARN of an existing public ACM certificate (if using a custom domain). |

## 4. One-Time Setup: Configuring GitHub OIDC in AWS

### Method 1: Using the Included Shell Script
```bash
chmod +x scripts/setup_oidc_role.sh
./scripts/setup_oidc_role.sh <YOUR_GITHUB_USERNAME_OR_ORG> <YOUR_REPO_NAME> us-east-1
```
The script will output the exact `AWS_ROLE_ARN` to copy into GitHub Secrets.

### Method 2: Bootstrapping via Terraform
1. In `terraform/terraform.tfvars`, set:
   ```hcl
   create_github_oidc_role = true
   github_repo             = "my-org/savitara-infotel-aws"
   ```
2. Run `terraform apply` locally once to provision the OIDC provider and IAM role.
3. Copy the output `github_actions_role_arn` into GitHub Secrets.

## 5. Workflow Execution Walkthrough

### 1. Pull Request Verification
When a developer opens a Pull Request against `main`:
1. The `lint-and-validate` job runs `terraform fmt -check` and `terraform validate` across root and environment modules.
2. The `security-scan` job runs `trivy` to detect security misconfigurations.
3. The `terraform-plan` job assumes the AWS OIDC role and generates a speculative execution plan.
4. The plan status and summary are posted directly to the PR comment thread.

### 2. Main Branch Deployment
When the PR is merged into `main`:
1. The workflow triggers automatically.
2. The `terraform-apply` job downloads the validated plan artifact.
3. Executes `terraform apply -auto-approve tfplan`.
4. State is locked in DynamoDB during apply to prevent concurrent modifications.
5. Deployed endpoints (HTTPS Application URL, Health Check URL, RDS Endpoint) are formatted into a markdown table in GitHub Actions Job Summary (`$GITHUB_STEP_SUMMARY`).
